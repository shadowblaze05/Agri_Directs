AGRI-DIRECT SYSTEM DOCUMENTATION
===============================

OVERVIEW
--------
Agri-Direct is a Flask-based agricultural marketplace and information platform for farmers, buyers, and administrators. The current project is organized around a clean package structure under app/ and keeps legacy files archived separately so the active code remains easy to maintain.

The project includes:
- user authentication and role-based access
- farm inventory management
- marketplace listings and transaction flow
- analytics and market intelligence pages
- knowledge hub content
- admin functions
- chat and notification features
- PostgreSQL-backed persistence through Flask-SQLAlchemy

This documentation reflects the current project state after the reorganization and cleanup process.

MARKET INTELLIGENCE SERVICE LAYER
--------------------------------
The project now includes a dedicated market intelligence service package in
app/services/market_intelligence. It follows the real project data model instead
of creating a greenfield schema and works against the current inventory, crop,
and marketplace tables.

Core service modules:
- criteria_builder.py: builds the AHP comparison matrix and derives stable
  criterion weights using pyDecision's ahp_method.
- supply_analysis.py: calculates dynamic thresholds and classifies each crop as
  balanced, undersupplied or oversupplied.
- demand_forecasting.py: builds short-horizon ARIMA demand forecasts and falls
  back to linear estimation when the dataset is too short for a robust model.
- demand_baseline.py: computes an OLS baseline for side-by-side comparison with
  the forecast and exposes the regression statistics.
- crop_recommendation.py: uses the weighted criteria and TOPSIS ranking to
  generate a crop recommendation score.
- data_sources/*.py: abstract the live data access for inventory, supply, and
  price monitoring so future data sources can slot in without changing route code.

The HTTP endpoints in app/routes/home.py now call analyze_market_intelligence() as
primary logic while keeping the existing build_market_analysis() response shape
for compatibility with legacy tests and dashboard consumers.

EXTENSIONS AND INIT ORDER
-------------------------
The correct extension order is defined in app/extensions.py and app/__init__.py.

Extensions:
- db = SQLAlchemy()
- migrate = Migrate()
- bcrypt = Bcrypt()
- login_manager = LoginManager()

Application initialization pattern:
1. create Flask app
2. load config from app/config.py
3. initialize db
4. initialize migrate
5. initialize bcrypt
6. initialize login_manager
7. register routes

This avoids circular import problems and keeps the app package clean.

DATABASE AND MIGRATION NOTES
----------------------------
Database backend:
- PostgreSQL is the target database backend.
- SQLite compatibility code is preserved only as a legacy transition layer.
- The current project does not replace PostgreSQL with SQLite.

Adding another admin user:
- This project does not use Django's built-in `createsuperuser` feature.
- In Flask, an administrator is simply a user row with `role = 'admin'`.
- The default admin is created during app initialization in app/models/database.py.
- The relevant behavior is:
  - check whether the username `admin` exists in the `users` table
  - if it does not exist, insert a new row with username `admin`, password = `generate_password_hash('admin')`, and role = `admin`
- This means the admin login is stored in the database, not in a special Flask superuser system.

To add another admin using the app:
1. Register a normal user via the registration page.
2. Update that user's role in the database:
   UPDATE users SET role = 'admin' WHERE username = 'your_username';

To add another admin manually in PostgreSQL:
1. Generate a Werkzeug-compatible password hash from the project virtual environment:
   .\.venv\Scripts\python.exe -c "from werkzeug.security import generate_password_hash; print(generate_password_hash('MyStrongPassword123'))"
2. Copy the hash output.
3. Run a SQL insert like this:
   INSERT INTO users(username, password, role) VALUES ('newadmin', 'PASTE_HASH_HERE', 'admin');
4. If you already created the user and only need to promote them, use:
   UPDATE users SET role = 'admin' WHERE username = 'newadmin';

Important:
- Do not store a plain-text password in the `password` column for this app.
- The login flow checks `check_password_hash(user['password'], password)`, so the value must be a Werkzeug hash, not raw text.
- If the user is created through the normal registration route, the app already hashes the password automatically in app/routes/auth.py.

Migration behavior:
- Flask-Migrate remains configured and active through app/extensions.py.
- The application must not run flask db migrate or flask db upgrade unless a real model change is intentionally made.
- The project currently avoids schema modifications during reorganization.

Schema helpers and compatibility layer:
- app/models/database.py contains legacy schema initialization and compatibility helpers.
- This file must be handled carefully because it still contains legacy SQLite-style SQL patterns.
- It is not safe to move or rename database tables without confirming PostgreSQL compatibility.

TESTING AND RUNNING
-------------------
To run locally:
1. Activate the virtual environment.
2. Set required values in .env.
3. Install dependencies if needed: pip install -r requirements.txt
4. Run: python run.py

Important:
- Do not run flask db migrate or flask db upgrade unless a real schema change is intended.
- If PostgreSQL is not configured correctly, the app will fail at runtime before routes load.

AGRI-DIRECT SYSTEM DOCUMENTATION
===============================

OVERVIEW
--------
Agri-Direct is a Flask-based agricultural marketplace and information platform for farmers, buyers, and administrators. The current project is organized around a clean package structure under app/ and keeps legacy files archived separately so the active code remains easy to maintain.

The project includes:
- user authentication and role-based access
- farm inventory management
- marketplace listings and transaction flow
- analytics and market intelligence pages
- knowledge hub content
- admin functions
- chat and notification features
- PostgreSQL-backed persistence through Flask-SQLAlchemy

This documentation reflects the current project state after the reorganization and cleanup process.

MARKET INTELLIGENCE SERVICE LAYER
--------------------------------
The project now includes a dedicated market intelligence service package in
app/services/market_intelligence. It follows the real project data model instead
of creating a greenfield schema and works against the current inventory, crop,
and marketplace tables.

Core service modules:
- criteria_builder.py: builds the AHP comparison matrix and derives stable
  criterion weights using pyDecision's ahp_method.
- supply_analysis.py: calculates dynamic thresholds and classifies each crop as
  balanced, undersupplied or oversupplied.
- demand_forecasting.py: builds short-horizon ARIMA demand forecasts and falls
  back to linear estimation when the dataset is too short for a robust model.
- demand_baseline.py: computes an OLS baseline for side-by-side comparison with
  the forecast and exposes the regression statistics.
- crop_recommendation.py: uses the weighted criteria and TOPSIS ranking to
  generate a crop recommendation score.
- data_sources/*.py: abstract the live data access for inventory, supply, and
  price monitoring so future data sources can slot in without changing route code.

The HTTP endpoints in app/routes/home.py now call analyze_market_intelligence() as
primary logic while keeping the existing build_market_analysis() response shape
for compatibility with legacy tests and dashboard consumers.

DATABASE AND MIGRATION NOTES
----------------------------
Database backend:
- PostgreSQL is the target database backend.
- SQLite compatibility code is preserved only as a legacy transition layer.
- The current project does not replace PostgreSQL with SQLite.

Database names and connection selection:
- app/config.py reads DATABASE_URL first. If it is unset, it builds a PostgreSQL
  URL from POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_HOST, POSTGRES_PORT, and
  POSTGRES_DB. The configured fallback database name is AgriDirect; the
  checked-in .env.example also uses AgriDirect.
- DATABASE_URL takes precedence over all POSTGRES_* components. Set it to the
  intended database for each environment; the actual production database name
  cannot be known from source code alone.
- app/__init__.py defines a root-level database.db path for compatibility, but
  this is not the configured default SQLAlchemy database. Do not assume that
  this SQLite file is the active database.
- There is one application database. Market intelligence reads inventory data
  from it; it does not use a separate market-intelligence database.
- Flask-Migrate/Alembic records the applied revision in alembic_version.
  alembic_version is migration metadata, not a business-data table.

Key data relationships and behavior:
- inventory.crop_id and harvest.crop_id identify a row in crops. The inventory
  table retains crop_name for legacy compatibility; current intelligence joins
  inventory to crops for the crop name.
- marketplace.user_id identifies the seller; marketplace.crop_id identifies
  the crop when available. Marketplace cart/image rows reference listing IDs.
- User/profile coordinates are reference data; inventory coordinates and photo
  paths are harvest evidence. Exact GPS values must not be exposed publicly.
- analytics rows are derived summaries refreshed by update_analytics(); they
  are not the raw source of market-intelligence forecasts.
- A knowledge category/post/comment relationship is represented by IDs in the
  schema. Not all such references are declared as database foreign-key
  constraints in the current model definitions.
- No separate ORM tables/classes exist for orders, preorders, transactions,
  reliability history, or market forecasts; order and preorder states are
  stored in marketplace and computed analytics remain in analytics/in memory.

Adding another admin user:
- This project does not use Django's built-in `createsuperuser` feature.
- In Flask, an administrator is simply a user row with `role = 'admin'`.
- The default admin is created during app initialization in app/models/database.py.
- The relevant behavior is:
  - check whether the username `admin` exists in the `users` table
  - if it does not exist, insert a new row with username `admin`, password = `generate_password_hash('admin')`, and role = `admin`
- This means the admin login is stored in the database, not in a special Flask superuser system.

To add another admin using the app:
1. Register a normal user via the registration page.
2. Update that user's role in the database:
   UPDATE users SET role = 'admin' WHERE username = 'your_username';

To add another admin manually in PostgreSQL:
1. Generate a Werkzeug-compatible password hash from the project virtual environment:
   .\.venv\Scripts\python.exe -c "from werkzeug.security import generate_password_hash; print(generate_password_hash('MyStrongPassword123'))"
2. Copy the hash output.
3. Run a SQL insert like this:
   INSERT INTO users(username, password, role) VALUES ('newadmin', 'PASTE_HASH_HERE', 'admin');
4. If you already created the user and only need to promote them, use:
   UPDATE users SET role = 'admin' WHERE username = 'newadmin';

Important:
- Do not store a plain-text password in the `password` column for this app.
- The login flow checks `check_password_hash(user['password'], password)`, so the value must be a Werkzeug hash, not raw text.
- If the user is created through the normal registration route, the app already hashes the password automatically in app/routes/auth.py.

Migration behavior:
- Flask-Migrate remains configured and active through app/extensions.py.
- Geotag verification adds nullable location/evidence fields and safe defaults for existing records in migration b72c946fa310.
- Review the migration before applying it; do not reset or delete existing user or inventory data.

Schema helpers and compatibility layer:
- app/models/database.py contains legacy schema initialization and compatibility helpers.
- This file must be handled carefully because it still contains legacy SQLite-style SQL patterns.
- It is not safe to move or rename database tables without confirming PostgreSQL compatibility.

PUBLIC LANDING PAGE METRICS
---------------------------
The `/` route in app/routes/home.py renders app/templates/public_home.html with
metrics queried from the database at request time. The figures are not hard-coded
and are not persisted as historical snapshots:

- Buyers: distinct usernames from users with role `buyer` UNION nonblank
  marketplace `buyer_username` values. A username found in both sources counts
  once; recorded buyer usernames without user accounts count as well.
- Farm profiles: non-admin user accounts with first and last name, email, profile
  picture, profile photo capture timestamp, verified location, and a nonblank
  GPS-derived place.
- Product listings: all marketplace rows except `listing_type = 'looking_for'`,
  including rows that are no longer available.
- Market listings: marketplace rows with `status = 'available'`, excluding
  `looking_for` requests.
- Growth: the percentage change in non-`looking_for` marketplace rows created
  from the start of the current month through the current time versus the same
  elapsed day/time period in the previous month. If the previous period is empty,
  display `New` when the current period has rows, otherwise `0%`.
- Knowledge posts: knowledge posts whose status is `Published`.
- Process uptime: time elapsed since the current application process started.
  This is not a 96% availability claim and is not measured by an uptime monitor.

These public landing metrics are distinct from the signed-in `/home` portal and
the analytics dashboard at `/dashboard`.

GEOTAG-BASED CROP LOCATION VERIFICATION
---------------------------------------
Purpose and data flow:
- Profile completion for harvest requires first name, last name, email, a profile photo captured through the in-browser camera, the photo/GPS capture timestamp, and a GPS-derived farm location. Phone number and bio are optional. Both web and JWT harvest submissions reject incomplete profiles.
- The Profile editor provides camera capture only (no photo file picker). Browser Geolocation captures coordinates separately from the image, the server validates them, and OpenStreetMap Nominatim reverse-geocodes them. The GPS-derived place and its official PSGC hierarchy are saved as separate user location fields and displayed independently; coordinates remain private.
- Users must allow browser camera and location access; production camera/geolocation require HTTPS. The UI explains why these permissions are needed and discloses the Nominatim lookup.
- Manual harvest submission can include a crop/harvest photo and separately captured browser coordinates with a capture timestamp. CSV imports remain supported and are marked for manual review because they do not carry browser GPS/photo evidence.
- The JWT-protected `/api/harvest` endpoint validates optional coordinates and capture time, binds the record to the token owner, and returns proximity/distance separately; because this JSON endpoint does not accept photo evidence, its records remain `manual_review`.
- Uploaded crop evidence is limited to PNG/JPG/JPEG/WEBP image content and 5 MB. It is stored outside the public static directory and is served only to the record owner or an administrator.
- A reusable Haversine service validates coordinate ranges and calculates distance in meters. The configured limit is 15 km / 15,000 meters (`MAX_CROP_DISTANCE_METERS`, default 15000); distance less than or equal to the limit is `within_range`, and greater distance is `outside_range`.
- Missing or incomplete coordinates, profile reference, timestamp, or photo cause the submission to be marked `manual_review`. Administrators can review evidence and set the final status to `approved` or `rejected`; their username and review timestamp are recorded.
- `pending`, `within_range`, `outside_range`, `manual_review`, `approved`, and `rejected` are distinct workflow values. A proximity result is not automatically an administrative approval.

Privacy and limitations:
- Exact reference/crop coordinates are not exposed in public profile or inventory pages. Harvest evidence requires authentication and owner/admin authorization.
- The feature uses GPS coordinates submitted by the browser, validated server-side for numeric format and legal latitude/longitude ranges. This does not prove that the client supplied genuine GPS readings; GPS can be inaccurate or spoofed.
- Photos are supporting evidence, not the source of location. EXIF is not trusted because it can be removed or modified.
- Browser geolocation requires permission and, in production, HTTPS. Proximity does not prove user identity, crop authenticity, or ownership of farmland or produce; uncertain/missing data requires human review.
- Camera-only controls remove the ordinary file picker, but a client-submitted image/GPS pair cannot prove cryptographically that camera hardware or genuine GPS produced it.
- Reverse-geocoding sends the submitted coordinates to OpenStreetMap Nominatim and requires network/service availability; the displayed place name is approximate. PSGC matching uses the official city/municipality, province, region, and barangay API records when a match is available.

RUNTIME AND DATA FLOW
---------------------
1. run.py imports the Flask app and database initialization entry point from app.
2. app/__init__.py creates the Flask application, loads app/config.py, initializes
   Flask-SQLAlchemy, Flask-Migrate, Flask-Bcrypt, and Flask-Login, then registers
   app/routes through app/routes/__init__.py.
3. Route modules render Jinja templates or return JSON. Domain code is split
   between app/services/ and app/algorithms/.
4. app/models/database.py exposes the DB-API-like get_db() compatibility facade
   over Flask-SQLAlchemy for legacy route SQL. SQLAlchemy model classes live in
   app/models/.
5. The market intelligence service loads/normalizes inventory records and calls
   its supply, forecast, baseline, and recommendation services.

PostgreSQL is the configured target, normally through DATABASE_URL or the
POSTGRES_* variables. The compatibility layer translates a limited set of
SQLite-style SQL patterns; it does not make arbitrary SQLite SQL portable.
Flask-Migrate/Alembic migration files are in migrations/versions/.

Unless a route below says otherwise, its registered default method is GET.

REST API or a separate API server.

MARKET INTELLIGENCE MODELS AND ALGORITHMS
-----------------------------------------
There are two active analysis paths. The service pipeline is the primary
market-intelligence implementation used by the intelligence pages and APIs.
app/algorithms/market_analysis.py remains a standalone/compatibility analysis
path used by legacy consumers and as a fallback in the API routes.

Input and orchestration:
- data_sources/transaction_data.py normalizes accepted crop, quantity, date,
  and location field aliases and can load inventory joined to crops from the
  live database. The inputs are inventory/harvest observations, not completed
  sales or independently collected market-price feeds.
- data_sources/supply_data.py aggregates positive quantities by crop and month.
- analyze_market_intelligence() normalizes or loads records, then runs supply
  analysis, demand forecasting, a linear-regression baseline, and weighted crop
  recommendation. The result includes summary, price_monitoring, risk_alerts,
  recommendations, forecast, baseline, and criteria_weights.

| Component | Model/algorithm and behavior |
|---|---|
| SupplyAnalysisService | For each crop, computes mean and sample standard deviation of record quantities. Bounds are max(0, mean - std) and mean + std. Total crop quantity is compared with these bounds: at or below 80% of lower is critical_shortage; below lower is undersupply; above 125% of upper is oversupply; above upper is high_supply; otherwise balanced. Emits crop thresholds, risk signals, summary, and market pressure. |
| Price snapshot | Uses aggregate crop supply, supply share, and mean supply to form a heuristic index: 100 + (1 - crop share)*40 + (crop supply / mean supply)*5, clamped to 60..190. Labels Rising/Stable/Cooling and Strong demand/Balanced/Pressure by index thresholds. This is a modeled index, not a measured currency price. |
| DemandForecastingService | Fits statsmodels ARIMA(1,0,0) to each crop's ordered positive inventory quantities and forecasts one step. Empty/single-point or failed model fits use the fallback; predictions are clamped to zero or above. Output identifies arima, fallback-linear, or insufficient-data. |
| DemandBaselineService | Fits scikit-learn ordinary least squares with record index as x and quantity as y; predicts the next index and returns nonnegative baseline quantity, slope, and in-sample R-squared. Empty and one-point series have explicit simple results. |
| CriteriaBuilder / AHP | Five benefit criteria: demand_strength, supply_stability, seasonal_fit, price_opportunity, risk_balance. A fixed pairwise comparison matrix is column-normalized, row-averaged, and normalized to weights. The helper also calculates an AHP consistency ratio. |
| CropRecommendationService / TOPSIS | Derives a five-value metric vector for each crop, applies AHP weights after vector-normalizing each criterion, calculates positive/negative ideal solutions and Euclidean distances, then ranks by closeness to the positive ideal. |
| data_sources/price_data.py | Provides the price-monitoring snapshot from aggregate inventory supply; it does not query an external spot-price service. |
| Legacy build_market_analysis() | Groups inventory by crop/month, extrapolates the next point with an ordinary least-squares-style linear trend, estimates a capped heuristic price index (60..180), generates supply-pressure risk alerts, applies a hard-coded crop season map, and ranks its top three recommendations. |
| reliability_status(score) | Converts a numeric score to Not Yet Rated, Excellent (90+), Good (75+), Fair (60+), or Needs Improvement. The seller-rating flow separately calculates average buyer stars and labels it High/Medium/Low Reliability. |
| Geotag distance | geotag_service validates coordinate ranges and computes Haversine distance in meters against the farmer reference coordinates; configured threshold defaults to 15,000 meters. Distance is a proximity signal only, not proof or automatic approval. |

Interpretation limits:
- The demand forecast and price index are heuristics over stored inventory
  quantities; they are not trained on buyer demand, transaction volumes, or
  authoritative commodity-price history.
- Data sparsity, input ordering, duplicate observations, and inventory update
  practices affect outputs. ARIMA can fall back to the simple linear estimate.
- Recommendations are decision-support rankings, not agronomic guarantees.
- Proximity, a photo, a model score, or a crop season label does not establish
  identity, land ownership, crop authenticity, or product quality.

INTEGRATIONS, UPLOADS, AND SETTINGS
-----------------------------------
- python-dotenv loads .env; app/config.py configures DATABASE_URL (or PostgreSQL
  connection components), SECRET_KEY, JWT_SECRET, mail settings, and crop
  geotag thresholds. Production deployments must set strong secret values and
  credentials through the environment, not source control. The code has
  development fallback values for database credentials and signing secrets;
  replace them in every deployed environment.
- JWT helpers read JWT_SECRET from the process environment when the auth service
  is imported, and sign HS256 tokens with a 24-hour expiration. Set the same
  strong JWT_SECRET before application startup for issuance and verification.
- Profile geotagging uses requests-based reverse geocoding through OpenStreetMap
  Nominatim and PSGC location records when available. app/services/geo_service.py
  also supports a Google Maps API key when configured.
- Profile and crop images are validated using Pillow and have a 5 MB limit.
  Crop evidence is stored outside the public static tree and served through an
  authenticated owner/admin route; marketplace images are static listing media.
- Flask-Mail and the email service provide mail integration; notifications are
  stored in the notifications table and surfaced in the signed-in interface.
- app/static/ contains the site stylesheets, chat CSS/JavaScript, and committed
  sample upload images. app/templates/ contains the rendered page templates.
